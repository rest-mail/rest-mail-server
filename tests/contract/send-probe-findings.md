# sendMessage coverage blockers

Part of #1443. Reproduced on 2026-11-03 against main
`adae7081e31526cc68a71885e86914252b4a69fd`, with the checksum-verified pinned
Vertrag 0.42.0, a local API build and disposable PostgreSQL 16. This is a
diagnostic result, not a repair or permission to remove the ratchet entry.

## Reproduced cause

Run the coverage configuration generated by `tests/contract/probes.py`, with
the served description, the real `entrypoint.py` hooks, enrolled contract MFA
administrator and these selections:

```sh
CONTRACT_COVERAGE=1 CONTRACT_MFA_ADMIN="$scratch/mfa-admin.json" \
  "$scratch/bin/vertrag" run --config "$scratch/coverage.yml" \
  --sequence --phases coverage \
  --operation-id updateDomain --operation-id sendMessage
```

The configuration uses the local endpoint and its saved generated description.
It omits the topology's internal-mTLS endpoint override, as `reports.py` does
for a different endpoint, and drops the unmatched signing-key and snooze pins,
as `run.sh` does for a narrowed run. No request body is rewritten.

The result was:

```text
2 operation(s) covered over 3 body, parameter and argument target(s), 56 probe(s) sent, 0 finding(s), 14 valid probe(s) skipped because the operation fails as documented
/api/v1/messages/send > Send a message > 201 > application/json: 14 probe(s), its example answered 422, documented 201
```

The real database then held `sending_policy=bulk` and `dmarc_policy=reject` on
`restmail.test`. Sending the unchanged `valid` example directly returned:

```json
{"error":{"code":"list_unsubscribe_required","message":"The sender domain sends bulk mail, so every message needs list_unsubscribe"}}
```

Two existing hook assumptions combine to cause this:

- `off_the_admin_domain` looks for a `coverage:` name that Vertrag never gives
  before hooks. `updateDomain` therefore changes the fixture admin's domain
  instead of the disposable domain the hook intended.
- `set_the_admin_domains_policy` reads an absent `admin_domain_policy` stash
  entry as `""`. A cold process therefore skips the first request to clear an
  existing policy. The examples process cannot populate the coverage process's
  stash.

The existing sender-mailbox fixture is not the cause of this example failure.
A send-only run on clean state passes its example but reaches the description
failures below. A send-only replay is not proof of safety in the wider sequence.

## Why a fixture-only change is not shipped

A scratch copy of the real hooks changed only the cache comparison from
`hooks.stash.get("admin_domain_policy", "")` to
`hooks.stash.get("admin_domain_policy")`. This made the real example pass:

```text
1 operation(s) covered over 1 body, parameter and argument target(s), 32 probe(s) sent, 14 finding(s)
pass: POST /api/v1/messages/send > Send a message > 201 > application/json
```

All 14 newly reached valid probes answered 422. For example:

```text
probe: every required property present
body: {"from":"x"}
status: 422
```

The served `sendMessageDescription` requires only `from`, with `minLength: 1`.
It makes `to` optional, allows its empty list, and describes recipient items as
unconstrained strings. The handler requires a nonempty `to` and validates every
address. The generated minimal body is consequently not a usable send. The
`scheduled_at` generator also supplies a date in 2020, which the handler rightly
refuses: scheduling must be at least a minute ahead and within a year. These
are genuine description/state disagreements, not evidence for relaxing the
handler or rewriting probe bodies.

The fixture-only change would turn the existing skipped-probe debt into new
failures outside the empty coverage-findings baseline. Neither baseline is
changed, and the scratch hook change is not included.

## Additional diagnostic replay, not a proposed description

A separate scratch JSON copy added the missing `to` requirement, its
`minItems: 1`, a sender address format and recipient item address formats.
This was deliberately not the served description and is not an acceptance
proof. It separated the address/list findings from the scheduling finding.

That replay first exposed another real setup failure: the sender hook's
`POST /api/v1/accounts` uses the primary admin's session, which answers 403
`two_factor_required`. The same request through a real MFA administrator
session answered 201. After that manual fixture setup, replaying the scratch
schema with a 3.1-second request delay produced:

```text
1 operation(s) covered over 1 body, parameter and argument target(s), 34 probe(s) sent, 1 finding(s)
probe: "scheduled_at" at a string of the declared shape
body: {"from":"someone@example.com","scheduled_at":"2020-01-02T03:04:05Z","to":["someone@example.com"]}
status: 422
```

The database contained 13 new Sent copies from `someone@example.com`, but no
INBOX copies: the API logged `local delivery failed for recipient` with
`rejected: 550 DMARC policy reject for example.com`. There was no SMTP queue
worker in this local setup, and no generated-recipient queue rows remained.
This does not prove DNS/network isolation or successful delivery. The separate
#1161 delivery-fuzz-fixture work owns that isolation; it is not taken on here.
Nor does a request delay prove isolation from the topology's hour budget.

## Boundaries for a follow-up

- Describe the required nonempty recipient list and actual address policy.
  The pinned go-oapifly 0.35.0 field-tag vocabulary can express the list count
  but not its items' address format. `format` on a slice describes the slice,
  not its items. Do not silently replace the generated description with the
  handwritten oracle or add a test-only schema overlay to claim coverage.
- Address-policy changes need an owner decision. `mail.ValidateAddress` uses
  `net/mail.ParseAddress`, which accepts display-name addresses; changing the
  executable request to bare-email format tags could reject previously
  accepted recipients. A stricter binder can also change refusal order and
  field messages. No such behavior change is made here.
- A global `fuzz.pin` for `from` or `to` is not operation-scoped in Vertrag
  0.42.0. It would suppress probes on other operations and, for `to`, affect
  both string-valued and list-valued fields. It is not a narrow send repair.
- A scheduling pin needs named, gated examples for the scheduling probes it
  suppresses. A `scheduled_at: null` pin would keep coverage sends immediate,
  but must not replace the malformed/type and time-window proofs.
- Newly accepted probes send mail. Keep their destinations inside the
  topology, account for the shared minute/hour submission budget and exercise
  a wider message/draft/queue sequence before lowering the entry. New messages
  move literal IDs; see the README's message-ID warning.

No exclusions, pins, validation rules, production hooks or description changes
are added by this diagnostic change. The focused sender-hook tests now load
the real entrypoint and use the original transaction name, without a synthetic
coverage prefix. Policy selection is mocked in those tests; they do not claim
to prove policy persistence, rate-limit isolation or the full topology.

Local build verification passed with `go build ./...`. The focused Python
sender-hook suite passed all seven tests in `python:3.12-slim` with PyYAML.
The selected `./internal/api` tests passed against disposable PostgreSQL with
`-count=1`. The selected handler tests did not all pass; unmodified fixtures
returned 403 or 500 instead of their expected policy results, for example:

```text
--- FAIL: TestSendMessage_DocumentedPolicyRefusal
contract_sendmessage_examples_test.go:93: status 500, want 422; body {"error":{"code":"internal_error","message":"Failed to check the sender"}}
--- FAIL: TestSendMessage_DomainSendingPolicy/bulk
domain_sending_policy_test.go:116: status = 403, body {"error":{"code":"forbidden","message":"You are not authorized to send from this address"}}; want 422 list_unsubscribe_required
```

Those handler fixtures are not modified by this diagnostic change. No passing
handler-suite result is claimed.

The full E2E topology, whole-API ratchet and neighbouring-operation acceptance
remain unproven. Full E2E runs only in the merge queue; a green PR is not that
proof.
